EB-Agent 平台新需求预研  |  2026-09-15  |  红线：不触发风控、不封号
结论速览（TL;DR）
  1. 红线只有两条：① 绝不向微信「写入」（不发送 / 不回复 / 不群发 / 不加好友）；② 绝不「注入进程」或「伪造协议」。
  2. 风控主要盯「交互行为」，不盯「读取」。只读、且不经过微信网络协议的数据，服务端几乎拿不到可判定的信号。
  3. 推荐方案：安卓系统通知监听（只读）→ 本地汇总 → 投递到微信之外的渠道。风险等级低，成本可控。
  4. 明确排除：Hook 注入（WeChatFerry/wcferry）、协议模拟（wechaty pad）、UI 自动化发送（wxauto 群发）——这三类是封号重灾区。
  5. 本地数据库解密（chatlog 类）不推荐：技术上离线不可检测，但腾讯 2025-10 已向作者发函、2026-01 用 DMCA 下架了 4000+ 个相关仓库，法律与合规风险高。
  6. 不需要第二台手机。封号风险与「哪台手机」无关——通知监听是系统级 API，微信看不到它。装在主力机上，账号风险与装在闲置机上完全一样。要解决的是耗电 / 后台被杀 / 隐私三件事，不是封号。
决策更新（2026-09-15）：改走「电脑版微信」，完全不经过手机

1. 需求拆解

目标：个人微信里有大量投研群，消息量远超人工消化能力，希望每天自动产出一份「群消息总结」。

硬约束：不触发微信风控、更不能封号。这是压倒一切的前提。

容易被忽略的两条隐含约束：

  • 不能打扰群里其他人。任何「机器人进群 / 自动回复 / 群内发总结」都会立刻暴露，且是封号高危行为。
  • 总结结果应投递到微信之外。把总结发回微信 = 主动触发「发送行为检测」，等于自己往枪口上撞。

2. 先搞清红线：微信到底靠什么检测

根据公开的风控分析与实战案例，微信对第三方/自动化的检测是三维模型，任何单一维度异常都可能触发：

检测维度关键指标（示例阈值）触发后果
行为特征发送频率 > 20 条/分钟、固定间隔、机械点击精度、深夜批量操作临时限制发送
内容特征诱导分享关键词、敏感词、重复模板内容功能限制
环境特征网络地址异常变动、设备指纹、非官方客户端特征强制验证 / 封禁

处罚是渐进式的：一级预警（消息延迟）→ 二级限制（朋友圈/群聊禁用）→ 三级临时封禁（24–72 小时）→ 四级永久限制部分功能 → 五级账号永久冻结。

必封红线（碰一条就危险）
  • Hook / 注入类：Xposed / LSPosed / WeChatFerry / wcferry 等修改微信进程内存 → 检测概率极高，属「非官方客户端」直接证据。
  • 协议模拟类：逆向私有协议、wechaty pad 协议登录 → 圈内共识「黑产级别，别碰」。
  • 批量发送 / 加好友 / 群发：无论用什么技术实现，都是最高危行为。
  • 深夜批量操作：不符合人类作息的行为模式本身就是风控信号。
关键洞察：为什么「只读」相对安全？

风控的核心是识别「异常交互」——发消息、加人、改状态这些会与微信服务器产生写操作的举动。而在系统层读取通知栏或离线读取本地文件，不产生任何发往微信服务器的请求，服务端没有可判定的数据点。这就是「读写分离」能同时满足「可用」和「安全」的根本原因。

关于「本地数据库解密」为什么不推荐

这条路线技术上确实诱人——纯离线，微信服务端完全检测不到。但现实是：

  • 2025 年 7 月，腾讯首次向 GitHub 发通知要求下架相关工具，GitHub 当时未处理。
  • 2025 年 10 月，知名工具 chatlog 作者收到微信官方函件，指其核心功能存在合规风险，项目停止维护。
  • 2026 年 1 月，腾讯走 DMCA 法律流程，一次下架 4195 个仓库（明列 38 个 + 连带 fork）。
  • 使用前提是降级微信并永久关闭自动更新，维护成本高、随时失效。

结论：它能规避「风控」，但规避不了「法律与合规风险」。既然你的红线是「不触发风控甚至封号」，那更不该引入一个腾讯正在主动追责的路线。除非是纯个人自用、绝不上传、且自行承担风险，否则不建议。

4. 推荐架构：读写分离 + 永不回写

核心思想一句话：用系统原生只读通道把消息「取出来」，在微信之外完成汇总与投递，全程不向微信写入一个字节。

为什么这个架构安全：

  • 采集层用的是安卓系统给第三方应用开放的合法通道（无障碍/通知读取的公开 API），不注入、不改包、不抓协议，从系统视角看只是一个「增强版通知管理工具」。
  • 汇总层完全离线跑在你自己电脑上，数据不出本机。
  • 投递层刻意绕开微信——这是把风险压到最低的关键一步：没有任何写回微信的动作，就没有任何「异常交互」可被检测。

5. 落地步骤

1
就用主力机（无需第二台手机） 风险与设备无关：通知监听是系统级 API，微信看不到它，装在主力机上不会增加封号风险。要解决的是耗电 / 后台被杀 / 隐私三件事（见下方「主力机部署」）。若主力机是 iOS，改走 PC 微信路径或半自动导出。
2
目标群做两处设置 ① 关闭该群的「消息免打扰」（免打扰后系统不弹通知，就抓不到）；② 微信通知设置里打开「显示消息详情」，否则只能拿到「你收到一条消息」。
3
安卓端实现（两条路，二选一）
  • 低代码（推荐先试）：用 MacroDroid / Tasker，配置「收到微信通知」触发 → 「HTTP 请求」动作，把通知内容 POST 到电脑。无需写代码，半小时能跑通。
  • 自研（更稳）：写一个继承 NotificationListenerService 的小 App，自己控制去重、长文本拼接、断线重传。适合长期维护。
4
PC 端接入 EB-Agent 新增一个 wxgroup 项目模块（与现有 Data / Anno / Wechat 并列）： 接收接口 → SQLite 落库 → 按群/按天聚合 → 复用现有 LLM 客户端做汇总 → 前端新增「微信群日报」页面。
5
定时任务 每日收盘后（如 18:30）自动跑汇总，产出日报。可接入平台已有的任务/日志体系。
6
投递与监控 日报只推送到 EB-Agent 网页 / 企业微信群机器人 / 邮件；同时对「消息条数异常」「手机掉线」做告警。一旦微信出现任何「操作频繁」提示，立即停止采集。

主力机部署：风险不变，重点解决三件事

先纠正一个前提：封号风险跟「哪台手机」无关。通知监听走的是安卓系统给第三方应用开放的公开 API，不注入微信、不抓协议、不驱动客户端，微信服务端拿不到任何信号。所以把它装在主力机上，微信账号的风险与装在闲置机上完全一样。真正要解决的是下面三个工程问题。

问题表现解决办法
耗电常驻监听增加耗电用轻量工具（MacroDroid 本身极轻）；设置只在交易时段（如 9:00–18:00）监听
后台被杀国产 ROM 冻结后台 → 漏消息关闭该 App 的电池优化、锁定后台任务、加白名单；优先用「通知类」而非「无障碍类」实现
隐私顾虑一个 App 能读所有通知配置里只处理 com.tencent.mm 的通知，其余一律忽略；数据只走局域网、不联网；自研 App 代码完全可控

关键：只用「通知监听（NLS）」，不要用「无障碍服务（Accessibility）」。前者只读通知、微信不可见；后者能模拟点击、属自动化特征，风险明显更高。

6. 红线清单

✅ 可以做

  • 只读：通知监听、截图 OCR、人工复制
  • 用系统原生公开 API
  • 数据只存本机、只走局域网
  • 总结投递到微信之外的渠道
  • 投研群消息做脱敏后入库

⛔ 绝对不做

  • 发送 / 回复 / 群发 / 加好友
  • Hook 注入、Xposed、WeChatFerry
  • 协议登录、wechaty pad
  • 把总结发回微信群
  • 降级微信、关闭自动更新去适配工具
  • 把群消息原文上传到公网大模型

7. 局限与风险（诚实说清）

  • 会漏消息：通知监听只能抓「弹出来的通知」。免打扰群、系统杀后台、微信前台打开时、通知被聚合折叠时，都可能漏。
  • 拿不到历史：只能从开启监听那一刻起，无法回溯之前的群消息。
  • 长文本可能被截断：部分机型通知栏会截断长消息，需要做「拼接 + 标记不完整」处理。
  • iOS 不支持：只能用半自动导出方案。
  • 摘要质量取决于清洗：群消息噪音大（表情、闲聊、广告），需要按关键词/发言人做过滤再喂模型。
  • 「低风险」不等于「零风险」：即使是系统通道，若采集行为异常（如高频读写、异常进程行为）理论上仍可能被关注，因此仍建议用闲置机、保持低频。

8. 合规与隐私提示

  • 群消息包含他人的发言，属于个人信息。务必做到：仅自己设备、仅自己可见、不上传公网、不外传。
  • 上传到大模型前，建议对真人姓名、手机号、身份证等做脱敏（如「张三」→「成员A」）。
  • 参考腾讯对聊天记录导出工具的立场（2026-01 DMCA 事件），个人自用、不传播是底线。
  • 本方案定位为个人效率工具，不得用于骚扰、营销、群发等场景。

9. 下一步建议

建议先做「最小验证」，再决定是否重投入：

  1. Day 1：在主力机上装 MacroDroid，把 1–2 个核心投研群的通知 POST 到电脑的一个临时接收页，跑一整天（风险与闲置机相同，只多花一点电）。
  2. 评估覆盖率：对比手机上的实际消息条数，看抓到了多少（经验值 70%–90%）。
  3. 若覆盖率够用 → 在 EB-Agent 正式落地 wxgroup 模块 + 前端日报页。
  4. 若不够用 → 评估「半自动导出」补足，或与群主协商是否有公众号/星球等更规范的信源。
